# 사진 보관 정책 (보존 방어 구현, 기간 정리 미구현)

## #88 1차 안전 경계 — 검증·배포 대기

- 소식의 사진 제거는 JSON 참조만 제거한다. 원본·미리보기 파일은 물리 삭제하지 않는다.
- 신규 클라이언트는 정리 DELETE 자체를 보내지 않는다. 서버는 기존 클라이언트의 유효한 요청에도 `200 {retained:true, deleted:false, code:"IMAGE_CLEANUP_DEFERRED"}`를 반환한다.
- `retained`는 **이 동작에서 파일을 삭제하지 않았다**는 뜻이다. 파일 존재·완전한 업로드·DB 연결 성공을 확인했다는 뜻이 아니다.
- 저장이 성공하고 응답만 유실됐을 수 있으므로 실패·재예약·부분 업로드도 보수적으로 보존한다. 기존 사진 자동 삭제 queue는 사용하지 않는다.
- 현재 정책은 용량 절약보다 기존 자료 보호를 우선한다. 미완료·제거 파일 때문에 사용량이 늘 수 있어 별도 관찰이 필요하지만, 유료 전환은 하지 않는다.
- UI에서 사진을 제거해도 이미 알려진 공개 미리보기 URL은 계속 접근 가능할 수 있다. 개인정보 삭제·접근 철회 기능으로 안내하지 않는다.
- 실제 코드·TC 범위는 [#88 수정 기록](test-reports/2026-11-05-issue88-photo-retention-source.md)을 따른다. 실행 검증과 배포 완료를 뜻하지 않는다.

## 배경

글은 지난 소식으로 유지하되 원본 사진 용량을 줄이고, 향후 이전 사진 불러오기를 지원한다.

- 글·행사 날짜·책방 정보는 유지한다.
- 원본은 발행 월 기준 최근 3개월 보관한다. 예: 9월에는 7~9월.
- 작은 미리보기는 우선 유지하며 실제 사용량에 따라 정책을 재검토한다.
- 최근 소식에서 재사용하는 원본은 최초 업로드 날짜가 오래돼도 삭제 대상에서 제외한다.
- 초기에는 삭제 예정 목록 → 원본 ZIP 백업 다운로드 → 관리자 확인 후 정리한다.
- 원본이 없으면 불러오기 화면에 미리보기만 남아 있으며 고화질 재첨부가 필요하다고 표시한다.
- 기존 사진에 자동 소급 삭제하지 않는다. 파일 연결 참조 검사와 정확한 삭제 대상 확인을 구현한 후 별도로 승인받는다.

## 접근 보호와 별개인 경계

스테이징 Worker의 입장 암호는 Supabase 공개 미리보기 URL을 보호하지 않는다. 테스트 이미지의 공개 범위는 저장소 정책에서 별도로 검증한다. 원본은 비공개 원칙을 유지한다.

게시판에 별도로 업로드한 사진은 이 저장소 원본 삭제와 무관하다. 반면 이 서비스의 URL을 직접 참조한 외부 게시물은 삭제 시 깨질 수 있어 정리 전에 확인해야 한다.

## 후속 작업

- 사진 참조 모델·재사용 연결과 원본 존재 여부 필드 설계
- 달 경계/재사용/중복 참조/백업 실패/삭제 실패 TC
- 백업은 같은 저장소에 무기한 쌓지 않기
- 관리자 삭제 UI와 단계별 실패 복구; 현재 서비스의 자동 물리 삭제는 보류
- 오래된 frontend와 backend를 함께 롤백하면 이전 삭제 위험이 다시 생길 수 있으므로 정확한 fallback 배포물을 별도 검증
