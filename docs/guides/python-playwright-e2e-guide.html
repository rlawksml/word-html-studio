0. 브라우저를 보며 바로 실습하기

터미널 하나만 사용합니다. 실습기가 로컬 앱을 시작하고, 브라우저 테스트가 끝나면 자신이 시작한 앱만 종료합니다.

최초 1회 준비

cd e2e/python
python3 practice_runner.py setup

오늘 실습

python3 practice_runner.py check
python3 practice_runner.py demo

check는 Python·Node·설치 상태와 실습 포트가 비어 있는지 확인합니다. demo는 앱을 localhost:4173에서만 열고, 브라우저 동작을 0.7초 간격으로 보여 준 뒤 자동 종료합니다. 화면 없이 빠르게 확인하려면 python3 practice_runner.py test를 사용합니다.

  1. practice/test_practice.py를 열어 주석 1~5를 순서대로 읽습니다.
  2. demo를 실행해 검색, 소식 열기, 내용 확인, 닫기를 눈으로 봅니다.
  3. 파일 아래 TODO 1대로 검색어를 E2E에서 공개로 바꿉니다.
  4. demo를 다시 실행하고 1 passed를 확인합니다.
  5. TODO 3으로 일부러 실패를 만들어 첫 오류를 읽은 뒤 원래 문장으로 되돌립니다.
안전 범위: 실행기는 URL·암호·토큰 옵션을 받지 않습니다. 고정 loopback 주소와 메모리 mock만 쓰며 포트가 사용 중이면 다른 서버를 끄지 않고 중단합니다.

1. 먼저 큰 그림

E2E(End-to-End) 테스트는 사용자의 시작부터 결과까지를 실제 브라우저로 확인합니다. 이 구성은 로컬 앱만 열고 API 응답은 가짜 데이터로 바꿔 실제 DB를 건드리지 않습니다.

Python

테스트 순서를 적는 프로그래밍 언어입니다. 들여쓰기가 문장 묶음을 구분합니다.

pytest

test_ 함수를 찾고 준비물(fixture)을 주입한 뒤 성공과 실패를 모읍니다.

Playwright

Chromium을 열어 버튼 클릭, 글자 입력, 화면 표시 여부를 사람처럼 확인합니다.

pytest
테스트 발견
→
fixture
안전한 준비
→
Playwright
브라우저 조작
→
expect
결과 확인
단위 테스트와 차이: 단위 테스트가 작은 함수 하나를 확인한다면 E2E는 브라우저에서 사용자가 겪는 연결된 흐름을 확인합니다. 둘은 경쟁 관계가 아니라 서로 다른 위험을 잡는 짝입니다.

2. 파일을 지도처럼 읽기

e2e/python/ ├── requirements.txt # 설치할 Python 패키지와 버전 ├── pytest.ini # pytest 공통 옵션·marker ├── .env.example # 비밀값이 아닌 환경변수 이름 예시 ├── safety.py # 원격 URL을 실행 전에 차단 ├── conftest.py # 공통 fixture, mock API, 네트워크 통제 └── tests/ ├── test_safety.py # 안전장치 자체를 검증 └── test_smoke.py # 로그인 모양·버튼 클릭 핵심 흐름

테스트 한 줄 해석

app_page.get_by_role("button", name="E2E 공개 소식", exact=True).click()

app_page에서 → 접근성 역할이 button이고 → 이름이 정확히 “E2E 공개 소식”인 요소를 찾아 → 클릭하라는 뜻입니다. CSS 선택자보다 사용자가 보는 이름을 사용해 발표 중에도 읽기 쉽습니다.

expect(dialog).to_contain_text("로컬 mock 상세 내용")

상세 창 안에 기대한 문장이 실제로 나타날 때까지 기다려 확인합니다. 단순히 클릭 명령이 오류 없이 끝난 것만으로는 성공 처리하지 않습니다.

fixture란?

여러 테스트가 반복해서 쓰는 “준비물 생성 함수”입니다. app_page fixture는 안전한 URL, 가짜 책방 데이터, 네트워크 규칙이 적용된 브라우저 페이지를 준비합니다. 테스트 함수 매개변수에 app_page라고 쓰면 pytest가 자동으로 제공합니다.

3. 실제 데이터를 지키는 안전장치

  1. 주소 사전 검사: 명시적 포트가 있는 http://localhost, 127.0.0.1, ::1만 허용합니다.
  2. 외부 통신 차단: 브라우저가 허용된 로컬 origin 밖으로 HTTP(S) 요청을 보내면 중단합니다.
  3. API mock: workspace와 session 응답은 메모리에 만든 값으로 돌려주며 실제 DB·Storage에 연결하지 않습니다.
  4. 예상 밖 API 요청 감지: 정의되지 않은 API 요청은 method와 관계없이 차단하고 테스트 마지막에 실패로 보고합니다.
  5. 증거 최소화: trace, video, screenshot, HAR, storage state를 기본 생성하지 않아 비밀값 잔류 위험을 줄입니다.
발표 때 꼭 말할 경계: 화면에서 로그인처럼 보이지만 실제 계정 로그인은 아닙니다. 입력 문자열은 mock 응답으로 처리됩니다. 운영 URL과 원격 Staging에서는 로그인·상태 변경 테스트를 실행하지 않습니다.

실제 암호, API 키, 쿠키, 세션은 코드·명령 기록·스크린샷에 넣지 않습니다. .env.example의 꺾쇠 값은 형식만 보여 주는 placeholder입니다.

4. 발표 전 준비와 정확한 시연 순서

발표 전에 설치를 끝내고 전체 테스트를 한 번 통과시킨 뒤, 현장에서는 짧은 TC 하나만 창을 보이며 실행하는 것이 안정적입니다.

최초 1회 준비

cd e2e/python
python3 -m venv .venv
source .venv/bin/activate
python -m pip install -r requirements.txt
python -m playwright install chromium

터미널 1 — 웹 앱 실행

cd apps/web
npm ci
npm run dev

localhost:3000 준비 메시지가 뜬 터미널은 그대로 둡니다.

터미널 2 — 전체 안전 확인

cd e2e/python
source .venv/bin/activate
E2E_BASE_URL=http://localhost:3000 pytest -q

발표용 브라우저 시연

E2E_BASE_URL=http://localhost:3000 pytest tests/test_smoke.py \
  -k visitor_can_open_and_close --headed --slowmo 700
  1. 명령을 실행하기 전 “지금부터 방문자의 소식 열기·닫기를 검증합니다”라고 목적을 말합니다.
  2. 브라우저가 열리면 자동 클릭을 보여 줍니다. 시연 중 마우스로 개입하지 않습니다.
  3. 상세 내용이 확인되고 창이 닫힌 뒤 터미널의 1 passed를 보여 줍니다.
  4. “실제 DB 대신 mock 데이터를 썼고 외부 요청은 차단됩니다”라고 안전 경계를 다시 말합니다.
명령 읽는 법: -k는 이름에 해당 문자열이 있는 테스트만 선택하고, --headed는 브라우저 창을 보이며, --slowmo 700은 각 조작 사이를 700ms 늦춥니다.

5. PASS, FAIL, SKIPPED, BLOCKED 읽기

상태뜻발표 문장
PASSED준비, 조작, 기대 결과가 모두 정상“자동화한 범위에서 기대 결과를 확인했습니다.”
FAILED기대와 다르거나 실행 오류. 제품 버그라고 단정하기 전에 환경을 확인“첫 오류 위치부터 원인을 분리해 확인합니다.”
SKIPPED코드에 적힌 조건 때문에 의도적으로 미실행“조건이 충족되지 않아 테스트가 건너뛰어졌습니다.”
BLOCKEDpytest 자동 상태가 아니라 안전한 환경·승인·데이터가 없어 실행 불가하다는 보고 판단“실패가 아니라, 안전 조건이 없어 실행하지 않았습니다.”

성공 수치만 말하지 말고 테스트 대상, 로컬/mock 여부, 미검증 범위를 함께 말해야 결과가 과장되지 않습니다.

6. 자주 만나는 오류

증상먼저 확인할 것해결
Connection refused웹 개발 서버가 실행 중인지, 포트가 3000인지터미널 1에서 npm run dev를 실행하고 준비 메시지를 기다립니다.
browser executable 없음Chromium 설치 여부가상환경에서 python -m playwright install chromium을 실행합니다.
UnsafeBaseUrlHTTPS, 원격 주소, 포트 누락 여부http://localhost:3000처럼 로컬 HTTP와 포트를 명시합니다. 안전장치를 우회하지 않습니다.
fixture ... not founde2e/python에서 실행했는지, 패키지를 설치했는지현재 폴더와 활성화된 .venv를 확인합니다.
요소를 찾지 못해 timeout개발 서버 코드와 테스트의 버튼 문구가 같은지첫 실패 줄과 실제 화면을 비교합니다. 무작정 대기 시간을 늘리지 않습니다.
하지 말 것: 오류를 없애려고 운영 URL을 넣거나 안전장치를 삭제하지 않습니다. 실제 자격증명을 복사해 테스트하지도 않습니다.

7. 3분 발표 대본

0:00–0:30 — 목적
“이번 기초 구성의 목적은 사용자가 실제 브라우저에서 겪는 핵심 흐름을 Python으로 자동 확인하는 것입니다. 기존 Node 테스트는 유지하고 Python E2E를 별도로 추가했습니다.”

0:30–1:00 — 도구
“Python은 절차를 적는 언어, pytest는 테스트를 찾아 실행하고 결과를 모으는 도구, Playwright는 Chromium을 조작하는 도구입니다.”

1:00–1:35 — 구조와 안전
“사용자 행동은 test_smoke.py, 공통 브라우저 준비와 mock API는 conftest.py, 로컬 주소 강제는 safety.py가 담당합니다. 운영과 원격 Staging은 이동 전에 차단하며 실제 DB나 암호를 사용하지 않습니다.”

1:35–2:30 — 시연
“지금 방문자가 공개 소식을 열고 내용을 확인한 뒤 닫는 한 흐름을 실행합니다.” (발표용 명령 실행) “브라우저가 사람 대신 버튼을 클릭하고 expect가 실제 표시를 확인했습니다.”

2:30–3:00 — 결과와 한계
“터미널의 PASS는 이 로컬 mock 범위의 성공입니다. 실제 원격 로그인은 격리 환경과 승인된 테스트 데이터가 없으므로 BLOCKED이며 성공으로 주장하지 않습니다. 다음 단계는 안전한 Staging이 준비된 뒤 별도 승인 아래 실제 역할 TC를 확장하는 것입니다.”

8. 발표 직전 체크리스트

  • 노트북에서 pytest -q 전체 통과를 확인했다.
  • 인터넷 없이도 이 HTML 파일이 열리는지 확인했다.
  • 두 터미널의 글자 크기를 키우고 알림을 껐다.
  • 화면·명령 기록에 실제 암호, 키, 쿠키가 없다.
  • PASS의 범위가 “로컬 mock E2E”임을 말할 준비가 됐다.
  • 원격 로그인은 BLOCKED라는 한계를 숨기지 않는다.
이 문서는 저장소 안에서 오프라인으로 열리며 외부 폰트·스크립트·이미지를 사용하지 않습니다.
