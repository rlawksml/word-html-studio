## 0. 백업·복원 안전성

### TC-DR-001 · 백업 파일 무결성

- 우선순위/구분: P0 / 자동
- 사전조건: 저장소 밖에 생성한 백업 디렉터리
- 절차:
  1. `npm run backup:verify -- /절대/백업/경로`를 실행한다.
  2. DB JSON 한 파일 또는 복제한 사진 한 파일을 바꾼 테스트 fixture도 검증한다.
- 기대 결과:
  - 원본 백업은 모든 파일의 크기·SHA-256과 DB 행 수가 일치해 `PASS`다.
  - 변조된 fixture는 `FAIL`이며 복원 단계로 진행하지 않는다.

### TC-DR-002 · Production 복원 차단

- 우선순위/구분: P0 / 자동
- 절차:
  1. `APP_ENV=production`으로 복원 도구를 실행한다.
  2. 예상 Staging ref와 실제 URL ref를 다르게 설정한다.
  3. backup source fingerprint와 대상 fingerprint를 같게 설정한다.
- 기대 결과:
  - 세 경우 모두 Database·Storage 쓰기 전에 명령이 실패한다.
  - 실제 비밀값이나 URL은 테스트 로그에 출력되지 않는다.

### TC-DR-003 · 빈 Staging 실제 복원

- 우선순위/구분: P0 / 실제 Supabase Staging
- 사전조건: 운영과 분리된 빈 Staging, migration 적용, backup 검증 PASS
- 절차:
  1. 복원 dry-run에서 대상 ref, 빈 테이블·버킷, 예정 개수를 확인한다.
  2. `--execute`로 복원한다.
  3. 네 테이블과 원본·미리보기를 다시 읽고 manifest와 비교한다.
- 기대 결과:
  - 행 수·JSON fingerprint·사진 수·크기·SHA-256이 모두 일치한다.
  - Production에는 생성·수정·삭제 요청이 없다.
  - 하나라도 다르면 릴리스 판정은 `NO-GO`다.

### TC-DR-004 · Staging 부분 복원 안전 재개

- 우선순위/구분: P0 / 자동·실제 Supabase Staging
- 사전조건: 검증된 백업과 복원 도중 중단되어 백업의 일부만 존재하는 Staging
- 절차:
  1. `--resume` dry-run으로 기존 테이블·객체를 백업과 비교한다.
  2. 알 수 없는 객체와 해시가 다른 행·사진에서 재개가 거부되는지 확인한다.
  3. `--execute --resume`으로 검증된 누락 사진만 업로드한다.
- 기대 결과:
  - 백업과 정확히 같은 기존 데이터는 건너뛰고 누락 객체만 복원한다.
  - 중복 응답·일시 오류는 원격 파일 해시 확인, 업로드 최대 3회·검증 다운로드 최대 6회 재시도로 복구한다.
  - 최종 행·사진 수, 크기, SHA-256이 manifest와 일치한다.

### TC-DR-005 · Staging의 운영 Supabase 연결 차단

- 우선순위/구분: P0 / 자동·배포 설정
- 절차:
  1. Staging URL과 예상 project ref가 같고 운영 ref가 차단 목록에 있을 때 앱을 실행한다.
  2. 예상 ref를 다르게 설정하거나 차단 목록을 비운 상태를 검사한다.
  3. Staging URL 자체를 운영 ref로 설정한 상태를 검사한다.
- 기대 결과:
  - 올바른 Staging 조합만 연결된다.
  - 오설정은 Supabase 요청 전에 실패하며 운영 데이터에 요청을 보내지 않는다.
  - 새 변수가 없는 기존 Production은 v1.0 호환 동작을 유지한다.

### TC-DR-006 · Git 브랜치와 Sites 프로젝트 교차 연결 차단

### TC-DR-007 · migration 불변성·파괴적 변경 차단

- 우선순위/구분: P0 / 자동·CI
- 절차:
  1. migration SQL과 manifest SHA-256이 일치하는지 검사한다.
  2. 새 migration에 `DROP TABLE`, `DROP COLUMN`, `TRUNCATE`, `DELETE FROM`, 컬럼 이름·타입 변경을 각각 넣은 fixture를 검사한다.
  3. 기준 브랜치에 있던 SQL을 수정·삭제하고 CI 변경 검사를 실행한다.
- 기대 결과:
  - additive SQL과 새 파일 추가만 통과한다.
  - 기존 SQL 해시 불일치, 수정·삭제와 파괴적 SQL은 모두 배포 전에 실패한다.
  - 과거 migration의 알려진 레거시 SQL만 파일명과 규칙이 고정된 예외로 처리한다.

### TC-SUB-009 · 입력 중 URL 자동 저장과 완료 검증

### TC-SUB-010 · 행사 날짜 월 탐색과 추가 분리

## 11. 실행·정리 기준

### 배포 가능 조건

- 모든 P0 자동 테스트 통과
- `npm run lint`, `npm test`, `npm run build` 통과
- 실제 Supabase 통합 테스트는 분리 대상·쓰기 범위가 승인되고 기존 자료 보존이 검증되어야 함. 성공 QA 보관 합의를 우선하며, 정리를 승인하지 않은 자료는 그대로 보관
- `git diff --check` 통과
- 환경변수 값·작업 암호·Supabase 비밀키가 변경 파일에 없음
- 수동 P0 항목에서 실패가 있다면 배포하지 않고 원인과 재현 절차 기록

### 테스트 종료 정리

1. 실행 전 자료와 이번 신규 소유 자료를 구분한다. 기존 업무·보관 QA·성공 자료를 삭제/수정/초기화하지 않는다.
2. DB/Storage 정리는 별도 명시 승인과 검증된 소유 adapter가 있는 정확한 신규 실패 자료만 대상으로 한다. 승인/안전장치가 없으면 BLOCKED로 남긴다. 백업 검사를 통과시키려고 미참조 사진을 지우지 않는다.
3. 임대 해제도 이번 테스트 소유 세션/자원에 한정한다. 운영에서 세션·presence 상태를 변경하지 않는다.
4. 운영 확인은 무인증 GET/HEAD·로그 범위만 사용한다. 수치를 맞추려고 기존 데이터를 되돌리거나 덮어쓰지 않는다.
