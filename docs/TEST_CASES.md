# 동네책방 소식 스튜디오 테스트 케이스

이 문서는 기능 변경 후 반복 실행할 수 있는 회귀 테스트 기준입니다. 실제 운영 데이터를 직접 수정하는 수동 테스트는 테스트 전용 책방·발행 월을 사용하고, 종료 후 생성한 소식·사진·편집 잠금을 정리합니다.

## 문서 정보

- 기준 버전: `main`
- 최초 작성일: 2026-07-28
- 운영 주소: `https://bookstore-news-studio.rlawksml.chatgpt.site/`
- 자동 테스트 위치: `apps/web/tests/`
- 실행 명령: `npm run lint`, `npm test`, `npm run build`, `npm run test:integration:local`

## 우선순위와 실행 구분

| 구분 | 의미 |
|---|---|
| P0 | 입력 손실·권한 우회·사진 유실처럼 배포를 막아야 하는 핵심 시나리오 |
| P1 | 주요 사용자 흐름과 발행 결과에 직접 영향을 주는 시나리오 |
| P2 | 편의성·표시·보조 기능 시나리오 |
| 자동 | 코드 테스트 또는 실제 Supabase 통합 테스트로 반복 실행 |
| 수동 | 서로 다른 브라우저, 모바일 화면, 외부 게시판처럼 사람 확인이 필요한 항목 |
| 혼합 | 자동 보호 로직과 실제 화면 사용성을 함께 확인 |

## 공통 준비

- 환경 A: 소식 입력자용 데스크톱 브라우저
- 환경 B: 두 번째 입력자 또는 HTML 편집자용 별도 브라우저·시크릿 창
- 환경 C: 방문자용 모바일 기기 또는 로그인하지 않은 브라우저
- 테스트 전용 책방 1곳과 발행 월 1개
- 20MB 이하 JPEG·PNG 각 1장과 iPhone HEIC 1장
- 테스트 데이터 제목에는 `[테스트]`를 붙이고 종료 후 삭제
- 동일 브라우저의 여러 탭은 작업자 로그인 쿠키를 공유하므로 동시 작업 검증에는 사용하지 않음
- Production 점검은 공개 GET·읽기 전용 집계만 사용하고, 생성·수정·삭제 TC는 별도 Staging에서만 실행

## 0. 백업·복원 안전성

### TC-DR-001 · 백업 파일 무결성

- 우선순위/구분: P0 / 자동
- 사전조건: 저장소 밖에 생성한 백업 디렉터리
- 절차:
  1. `npm run backup:verify -- /절대/백업/경로`를 실행한다.
  2. DB JSON 한 파일 또는 복제한 사진 한 파일을 바꾼 테스트 fixture도 검증한다.
- 기대 결과:
  - 원본 백업은 모든 파일의 크기·SHA-256과 DB 행 수가 일치해 `PASS`다.
  - 변조된 fixture는 `FAIL`이며 복원 단계로 진행하지 않는다.

### TC-DR-002 · Production 복원 차단

- 우선순위/구분: P0 / 자동
- 절차:
  1. `APP_ENV=production`으로 복원 도구를 실행한다.
  2. 예상 Staging ref와 실제 URL ref를 다르게 설정한다.
  3. backup source fingerprint와 대상 fingerprint를 같게 설정한다.
- 기대 결과:
  - 세 경우 모두 Database·Storage 쓰기 전에 명령이 실패한다.
  - 실제 비밀값이나 URL은 테스트 로그에 출력되지 않는다.

### TC-DR-003 · 빈 Staging 실제 복원

- 우선순위/구분: P0 / 실제 Supabase Staging
- 사전조건: 운영과 분리된 빈 Staging, migration 적용, backup 검증 PASS
- 절차:
  1. 복원 dry-run에서 대상 ref, 빈 테이블·버킷, 예정 개수를 확인한다.
  2. `--execute`로 복원한다.
  3. 네 테이블과 원본·미리보기를 다시 읽고 manifest와 비교한다.
- 기대 결과:
  - 행 수·JSON fingerprint·사진 수·크기·SHA-256이 모두 일치한다.
  - Production에는 생성·수정·삭제 요청이 없다.
  - 하나라도 다르면 릴리스 판정은 `NO-GO`다.

### TC-DR-004 · Staging 부분 복원 안전 재개

- 우선순위/구분: P0 / 자동·실제 Supabase Staging
- 사전조건: 검증된 백업과 복원 도중 중단되어 백업의 일부만 존재하는 Staging
- 절차:
  1. `--resume` dry-run으로 기존 테이블·객체를 백업과 비교한다.
  2. 알 수 없는 객체와 해시가 다른 행·사진에서 재개가 거부되는지 확인한다.
  3. `--execute --resume`으로 검증된 누락 사진만 업로드한다.
- 기대 결과:
  - 백업과 정확히 같은 기존 데이터는 건너뛰고 누락 객체만 복원한다.
  - 중복 응답·일시 오류는 원격 파일 해시 확인, 업로드 최대 3회·검증 다운로드 최대 6회 재시도로 복구한다.
  - 최종 행·사진 수, 크기, SHA-256이 manifest와 일치한다.

### TC-DR-005 · Staging의 운영 Supabase 연결 차단

- 우선순위/구분: P0 / 자동·배포 설정
- 절차:
  1. Staging URL과 예상 project ref가 같고 운영 ref가 차단 목록에 있을 때 앱을 실행한다.
  2. 예상 ref를 다르게 설정하거나 차단 목록을 비운 상태를 검사한다.
  3. Staging URL 자체를 운영 ref로 설정한 상태를 검사한다.
- 기대 결과:
  - 올바른 Staging 조합만 연결된다.
  - 오설정은 Supabase 요청 전에 실패하며 운영 데이터에 요청을 보내지 않는다.
  - 새 변수가 없는 기존 Production은 v1.0 호환 동작을 유지한다.

### TC-DR-006 · Git 브랜치와 Sites 프로젝트 교차 연결 차단

- 우선순위/구분: P0 / 자동·CI
- 절차:
  1. `develop` 대상 PR에서 Staging Sites project ID를 검사한다.
  2. `main` 대상 PR과 `main` push에서 Production Sites project ID를 검사한다.
  3. 두 project ID를 서로 바꾼 조합과 알 수 없는 대상을 검사한다.
- 기대 결과:
  - 브랜치와 Sites 프로젝트가 올바른 조합일 때만 CI가 진행된다.
  - `develop`의 Staging 설정이 release PR을 통해 `main`에 그대로 들어가면 배포 전에 실패한다.
  - GitHub의 실제 Supabase 통합 테스트는 `staging` Environment Secret만 사용한다.

### TC-DR-007 · migration 불변성·파괴적 변경 차단

- 우선순위/구분: P0 / 자동·CI
- 절차:
  1. migration SQL과 manifest SHA-256이 일치하는지 검사한다.
  2. 새 migration에 `DROP TABLE`, `DROP COLUMN`, `TRUNCATE`, `DELETE FROM`, 컬럼 이름·타입 변경을 각각 넣은 fixture를 검사한다.
  3. 기준 브랜치에 있던 SQL을 수정·삭제하고 CI 변경 검사를 실행한다.
- 기대 결과:
  - additive SQL과 새 파일 추가만 통과한다.
  - 기존 SQL 해시 불일치, 수정·삭제와 파괴적 SQL은 모두 배포 전에 실패한다.
  - 과거 migration의 알려진 레거시 SQL만 파일명과 규칙이 고정된 예외로 처리한다.

### TC-DR-008 · v1.1 → v1.0.1 → v1.1 JSON 왕복 보존

- 우선순위/구분: P0 / 자동·실제 Supabase Staging
- 사전조건: 스키마 `202609070001`이 적용된 분리된 Staging과 테스트 전용 Submission
- 절차:
  1. v1.1 전용 최상위·중첩 JSON 필드가 있는 소식을 테스트 행에 저장한다.
  2. 미래 필드를 보내지 않는 v1.0.1 요청으로 제목·운영 안내를 수정한다.
  3. DB 원본 JSON을 다시 읽고 v1.1 전용 필드와 현재 필드를 비교한다.
  4. 소식·사진을 삭제한 요청도 보내 삭제 항목이 되살아나지 않는지 확인한다.
- 기대 결과:
  - 미래 필드와 v1.0.1에서 수정한 기존 필드가 모두 보존된다.
  - 요청 배열 순서는 유지되고 사용자가 삭제한 항목은 되살아나지 않는다.
  - 테스트 전용 행만 정리하며 기존 데이터는 변경되지 않는다.

### TC-DR-009 · 기간 일정 별도 저장소 롤백 보존과 원자 저장

- 우선순위/구분: P0 / 실제 Supabase Staging
- 사전조건: 스키마 `202609070002`가 적용된 분리된 Staging과 고유 ID의 테스트 전용 Submission
- 절차:
  1. v1.1 API로 테스트 전용 Submission 본문과 시작일·종료일을 저장한다.
  2. `submissions.news` JSON에는 기간 키가 없고 별도 테이블의 활성 행에만 기간이 있는지 확인한다.
  3. 기간 필드를 보내지 않는 v1.0.1 형태 요청으로 같은 Submission의 기존 필드를 저장한다.
  4. 기간 행의 시작일·종료일을 다시 읽는다.
  5. 종료일이 시작일보다 빠른 요청을 보내 본문과 기간이 모두 갱신되지 않는지 확인한다.
  6. 기간을 변경·해제·재등록해 본문과 기간의 원자 저장 및 비활성화를 확인한다.
  7. `/api/version`을 확인하고 `finally`에서 테스트 전용 행만 정확한 ID로 정리한다.
- 기대 결과:
  - v1.0.1 저장 후에도 기간 행이 정확히 유지된다.
  - v1.1 저장 응답과 공개 Workspace에는 기간이 결합되지만 기존 JSONB에는 섞이지 않는다.
  - 잘못된 기간은 `INVALID_SCHEDULE_RANGE`와 정확한 필드 경로로 거부되고 부분 저장이 없다.
  - API는 제품 `1.1.0-rc.1`, DB `202609070002`를 식별한다.
  - 기존 Staging 행 수·사진 manifest는 테스트 전후가 같다.

### TC-DR-010 · GitHub Actions 지원 런타임 유지

- 우선순위/구분: P1 / 자동·CI
- 절차:
  1. `verify`와 `supabase-integration` job의 checkout·Node 설치 action 버전을 검사한다.
  2. PR 검증과 수동 Staging 통합 workflow를 각각 실행한다.
- 기대 결과:
  - 두 job 모두 GitHub가 지원하는 Node 24 기반 action major를 사용한다.
  - 기존 Node 22 애플리케이션 실행, npm cache, 전체 Git 이력, Staging Environment 설정은 유지된다.
  - Node.js 20 지원 종료 경고 없이 두 job이 통과한다.

### TC-DR-011 · Supabase 통합 테스트 QA 데이터 정리 검증

- 우선순위/구분: P1 / 자동·실제 Supabase Staging
- 사전조건: 운영과 분리된 Staging, 통합 테스트가 생성한 고유 2099년 ID와 Storage 경로
- 절차:
  1. 정리 단계 중 일부가 Supabase 오류를 반환하거나 예외를 던지는 대역으로 안전장치 단위 테스트를 실행한다.
  2. 앞 단계 실패와 관계없이 뒤의 정확한 정리 대상까지 모두 시도되는지 확인한다.
  3. 실제 Staging 통합 테스트 3건을 실행한다.
  4. 책방·Submission·기간 일정·편집 임대·개선사항을 테스트 키로 재조회한다.
  5. 원본·미리보기 Storage 객체를 테스트가 예약한 정확한 경로로 재조회한다.
- 기대 결과:
  - 정리 API 오류와 남은 QA 행·객체는 테스트 실패로 보고된다.
  - 한 정리 단계가 실패해도 나머지 정확한 대상의 정리를 계속 시도한다.
  - 정상 실행은 실제 삭제와 삭제 후 잔여 0건 확인을 모두 통과해야 성공한다.
  - 운영 Supabase와 기존 Staging 업무 데이터는 조회·수정·삭제하지 않는다.

## 1. 초기 로딩과 접속

### TC-LOAD-001 · 정상 초기 로딩

- 우선순위/구분: P0 / 자동·수동
- 사전조건: Supabase Database와 Storage 환경변수가 정상
- 절차:
  1. 로그인하지 않은 새 창에서 운영 주소를 연다.
  2. 초기 로딩 화면이 끝날 때까지 기다린다.
- 기대 결과:
  - 빈 흰 화면 대신 데이터 로딩 안내가 먼저 표시된다.
  - `/api/workspace` 성공 후 방문자 달력과 책방 소식이 표시된다.
  - 같은 요청이 불필요하게 반복되지 않는다.

### TC-LOAD-002 · 지연·실패 재시도

- 우선순위/구분: P1 / 자동
- 사전조건: 최초 데이터 요청을 지연 또는 실패하도록 테스트 대역 설정
- 절차:
  1. 첫 요청을 8초 이상 지연한다.
  2. 첫 번째와 두 번째 요청을 실패시키고 세 번째 요청을 성공시킨다.
  3. 세 요청을 모두 실패시키는 경우도 확인한다.
- 기대 결과:
  - 8초 후 지연 안내와 다시 시도 버튼이 표시된다.
  - 최대 3회까지만 자동 시도한다.
  - 최종 실패 시 빈 데이터로 오인하지 않고 연결 오류를 안내한다.

## 2. 작업자 접속과 세션

### TC-AUTH-001 · 입력자 암호와 자판 변환

- 우선순위/구분: P0 / 자동·수동 (`tests/access-code-normalization.test.mjs`)
- 절차:
  1. `소식 입력`을 선택한다.
  2. 한글 자판과 영문 자판 상태에서 각각 입력자 암호를 입력한다.
  3. 겹받침·복합 모음·쌍자음이 포함된 비밀값 없는 테스트 문자열을 변환한다.
  4. 다른 문자열과 영문 대소문자 차이를 입력한다.
- 기대 결과:
  - 두 자판 상태 모두 동일한 입력자 역할로 접속된다.
  - 환경변수에는 한 형태만 등록해도 두 입력을 동일한 두벌식 키 조합으로 판정한다.
  - 겹받침·복합 모음·쌍자음은 실제 Shift 키를 포함한 조합으로 정확히 변환된다.
  - 다른 문자열과 영문 대소문자 차이는 계속 거부된다.
  - 실제 암호 값은 HTML·브라우저 번들·Git 저장소에 포함되지 않는다.

### TC-AUTH-002 · 역할별 API 권한

- 우선순위/구분: P0 / 자동
- 절차:
  1. 방문자 세션으로 책방·소식·사진 원본 변경 API를 호출한다.
  2. HTML 편집자 세션으로 입력자 전용 저장 API를 호출한다.

### TC-AUTH-004 · 동일 브라우저 다중 탭

### TC-SUB-004 · 입력 완료 서버 확인

  2. `입력 마무리`를 누른다.

- 기대 결과:
  - 서버 저장 성공 후에만 목록으로 이동하고 `입력 완료`가 표시된다.

  2. 제목 또는 상세 내용을 수정한다.
- 기대 결과:
  - 상태가 자동으로 `작성 중`으로 전환된다.
  - 이미 게시된 소식이면 재게시 필요 상태가 표시된다.

### TC-SUB-006 · 지난달 내용 복사

- 우선순위/구분: P1 / 수동
- 절차:

  2. 새 발행 월에서 `지난달 소식 불러오기`를 누른다.
- 기대 결과:
  - 이전 달 원본은 변경되지 않는다.
  - 새 달의 독립적인 작성 중 소식으로 복사된다.

### TC-SUB-007 · 저장하지 않고 이동

- 우선순위/구분: P0 / 자동·수동
- 절차:
  1. 이미 한 번 자동 저장된 소식의 제목과 상세 내용을 다시 수정한다.
  2. 자동 저장이 실행되기 전에 `← 책방 목록`, 로고 또는 로그아웃을 누른다.
  3. 이탈 안내에서 `계속 작성`을 눌러 화면에 남는지 확인한다.
  4. 다시 이탈 안내를 열고 `저장하지 않고 이동`을 선택한다.
  5. 같은 책방에 다시 들어간다.
- 기대 결과:
  - 안내에는 `임시 저장 후 이동`, `계속 작성`, `저장하지 않고 이동`이 모두 표시된다.
  - `계속 작성`은 현재 입력을 그대로 유지한다.
  - `저장하지 않고 이동`은 예약된 자동 저장과 탭 임시 복구본을 취소한다.
  - 마지막으로 서버가 확인한 자동 저장 내용까지만 복원되고 그 이후 수정은 사라진다.
  - 한 번도 서버에 저장되지 않은 새 소식은 빈 임시 레코드로 남지 않는다.
  - 사진 업로드 중에는 세 선택지 모두 이동을 실행하지 않는다.

### TC-SUB-008 · 한글 IME 직후 입력 마무리

- 우선순위/구분: P0 / 자동·수동
- 절차:
  1. 소식 제목에 `신규모집`을 한글 IME로 입력하고 마지막 글자 직후 마우스로 `입력 마무리`를 누른다.
  2. 상세 내용과 선택 입력에도 마지막 한글을 입력한 직후 Tab·Enter·마우스로 포커스를 옮겨 완료한다.
  3. 영문 입력과 붙여넣기도 같은 방식으로 확인한다.
  4. 저장 응답의 제목·본문·선택 입력 중 하나를 요청과 다르게 만들어 완료를 시도한다.
  5. 같은 시나리오를 반복하고 다시 편집 화면에 들어가 서버 값을 확인한다.
- 기대 결과:
  - 완료 스냅샷은 이전 렌더가 아니라 동기 ref의 최신 입력으로 만들어진다.
  - 조합 중에는 완료 저장을 시작하지 않고, 포인터 완료는 활성 입력을 먼저 확정한다.
  - 제목·상세 내용·선택 입력의 마지막 글자까지 서버 응답과 일치한다.
  - 서버의 UTC 시각 표현과 JSONB 객체 키 순서가 달라도 사용자 본문이 같으면 완료된다.
  - 서버 응답이 요청과 다르면 목록으로 이동하지 않고 작성 중 상태와 탭 복구본을 유지한다.

### TC-SUB-009 · 입력 중 URL 자동 저장과 완료 검증

- 우선순위/구분: P0 / 자동·통합·브라우저
- 절차:
  1. 소식의 대표 신청 링크 또는 두 번째 관련 링크에 `https:/`처럼 아직 완성되지 않은 주소를 입력한다.
  2. 제목·상세 내용을 추가로 수정하고 1.2초 뒤 자동 저장 상태와 재진입 값을 확인한다.
  3. 불완전한 주소를 유지한 채 `입력 마무리`를 누른다.
  4. `www.example.com`, `https://example.com`을 차례로 입력해 보완·완료 동작을 확인한다.
  5. 소식 1·5·10·20개에 정상·불완전 URL을 섞어 첫 오류 위치를 확인한다.
- 기대 결과:
  - 작성 중인 `draft`는 부분 URL 때문에 월별 소식 전체 자동 저장이 실패하지 않는다.
  - 입력 완료는 첫 잘못된 URL을 `소식 n → 대표 신청 링크` 또는 `소식 n → 관련 링크 m`으로 안내하고 해당 선택 영역을 펼쳐 포커스한다.
  - `www.example.com`은 포커스를 벗어나거나 완료할 때 `https://www.example.com`으로 보완된다.
  - 완전한 http/https URL만 완료되고, 불완전하거나 위험한 URL은 방문자·HTML 결과의 링크로 출력되지 않는다.
  - API 400 응답은 `code=INVALID_URL`, `fieldPath`, `message`를 포함하고 서버 로그에는 본문 없이 오류 종류·위치·요청 크기만 남는다.

### TC-SUB-010 · 행사 날짜 월 탐색과 추가 분리

- 우선순위/구분: P1 / 자동·브라우저
- 절차:
  1. 기존 행사 날짜가 한 개 이상 있는 소식을 연다.
  2. 날짜 선택기에서 이전 달·다음 달로 이동하되 `날짜 추가`는 누르지 않는다.
  3. 날짜 하나를 고른 뒤 `날짜 추가`를 누른다.
  4. 같은 날짜를 다시 고르고, 추가된 날짜 중 하나만 삭제한다.
  5. 발행 연도와 다른 연도의 날짜도 추가한다.
- 기대 결과:
  - 월을 탐색하거나 날짜를 임시로 고르는 것만으로 `dates[]`가 바뀌지 않는다.
  - `날짜 추가`를 누른 날짜만 정확히 한 번 등록된다.
  - 중복 날짜는 추가되지 않고, 한 날짜를 삭제해도 나머지 날짜는 유지된다.
  - 발행 연도와 다른 날짜에는 연도가 함께 표시된다.
  - 기존 `dates[]` 저장 구조와 방문자 달력·HTML 출력은 변하지 않는다.

### TC-SUB-011 · 장기 행사 시작일·종료일 기간 입력

- 우선순위/구분: P0 / 자동·통합·브라우저
- 절차:
  1. 소식 일정에서 `기간 입력`을 선택하고 시작일만 고른 뒤 적용한다.
  2. 종료일을 시작일보다 빠르게 고른 뒤 적용한다.
  3. `2026-06-17`부터 `2026-08-12`까지를 선택하고 `기간 적용`을 누른다.
  4. 6월·7월·8월과 앞뒤 달의 방문자 달력을 확인한다.
  5. 방문자 상세, 입력자 미리보기와 개별 HTML의 일정 문구를 확인한다.
  6. 시작일과 종료일이 같은 하루 기간, `2026-12-31`부터 `2027-01-02`까지의 연도 경계를 확인한다.
- 기대 결과:
  - 불완전하거나 역전된 기간은 저장값을 바꾸지 않고 해당 날짜 입력에 안내·포커스한다.
  - 유효한 기간은 두 날짜만 저장하고 6월 17일부터 8월 12일까지 모든 날짜에 표시된다.
  - 5월과 9월에는 표시되지 않으며, 상세와 HTML에는 `6월 17일~8월 12일`이 정확히 출력된다.
  - 하루 기간은 한 날짜로, 연도 경계는 양쪽 연도를 포함해 표시된다.
  - 개별 날짜 입력과 기간 입력은 동시에 활성화되지 않고 기존 `dates[]` 소식은 그대로 동작한다.

- 절차:

  2. 같은 파일에 `drop`과 `change`가 연달아 발생하는 환경을 확인한다.
- 기대 결과:
  - 한 번의 사용자 동작으로 중복 사진이 생기지 않는다.
  - 드롭 이벤트가 소식 카드 정렬 이벤트로 전파되지 않는다.

### TC-IMG-004 · 업로드 중 이동 차단

- 우선순위/구분: P0 / 자동·수동
- 절차:
  1. HEIC 또는 큰 JPEG 업로드를 시작한다.
  2. 완료 전에 뒤로가기·임시 저장·입력 마무리를 시도한다.
- 기대 결과:
  - 업로드 대상 입력과 저장·완료 버튼이 잠긴다.
  - 사진의 Storage 저장과 DB 연결이 끝난 뒤에만 이동할 수 있다.

### TC-IMG-005 · 서명 URL·네트워크 복구

- 우선순위/구분: P0 / 자동
- 절차:
  1. 첫 번째 Storage PUT에 네트워크 오류 또는 재시도 가능한 상태를 반환한다.
  2. 같은 서명 주소 재시도를 모두 실패시킨다.
- 기대 결과:
  - 같은 주소에서는 제한된 횟수만 재시도한다.
  - 이후 새로운 서명 URL을 발급받아 다시 전송한다.
  - 최종 실패한 임시 경로는 DB에 연결하지 않는다.

### TC-IMG-006 · 잘못된 파일과 용량 제한

- 우선순위/구분: P0 / 자동
- 절차:

  2. 20MB 초과 이미지를 선택한다.

- 기대 결과:
  - 지원하지 않는 형식·초과 용량·미리보기 변환 실패를 구분해 안내한다.
  - 부분 저장된 원본·미리보기와 DB 참조를 남기지 않는다.

### TC-IMG-007 · 사진 삭제 실패 복구

- 우선순위/구분: P1 / 자동·실제 Supabase 통합

- 기대 결과:

  - Storage 정리 실패는 별도로 안내하고 이후 재시도할 수 있다.

## 7. 동시 편집과 충돌

### TC-CONC-001 · 같은 책방 진입 잠금

- 우선순위/구분: P0 / 실제 Supabase 통합·수동
- 절차:
  1. 환경 A에서 책방과 월을 열어둔다.
  2. 환경 B에서 같은 책방과 월에 들어간다.
- 기대 결과:
  - 환경 B는 안내 팝업만 보고 편집 화면에 들어가지 않는다.
  - 다른 책방은 정상적으로 열 수 있다.

### TC-CONC-002 · 편집 임대 해제와 만료

- 우선순위/구분: P0 / 실제 Supabase 통합·수동
- 절차:
  1. 환경 A에서 목록으로 정상 이동한다.
  2. 환경 A를 강제 종료하는 경우도 확인한다.
- 기대 결과:
  - 정상 이동 시 임대가 즉시 해제된다.
  - 강제 종료 시 최대 3분 후 다른 작업자가 인계할 수 있다.
  - 다른 세션은 소유하지 않은 임대를 삭제할 수 없다.

### TC-CONC-003 · 낙관적 저장 충돌

- 우선순위/구분: P0 / 자동·실제 Supabase 통합
- 절차:
  1. 두 세션이 같은 `updated_at`을 가진 소식을 읽는다.
  2. 세션 A가 먼저 저장한다.
  3. 세션 B가 다른 내용으로 저장한다.
  4. 응답만 유실된 동일 내용 재시도도 확인한다.
- 기대 결과:
  - 다른 내용은 409로 막고 최신 내용 확인을 안내한다.
  - 서버에 이미 저장된 동일 내용이면 최신 버전을 이어받아 성공으로 복구한다.

### TC-SEC-001 · 운영 의존성 high 취약점 차단

- 우선순위/구분: P0 / 자동·Staging

## 11. 실행·정리 기준

### 배포 가능 조건

- 모든 P0 자동 테스트 통과
- `npm run lint`, `npm test`, `npm run build` 통과
- 실제 Supabase 통합 테스트가 테스트 데이터를 모두 정리하고 종료
