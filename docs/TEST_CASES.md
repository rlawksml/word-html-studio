# 동네책방 소식 스튜디오 테스트 케이스

이 문서는 기능 변경 후 반복 실행할 수 있는 회귀 테스트 기준입니다. 실제 운영 데이터를 직접 수정하는 수동 테스트는 테스트 전용 책방·발행 월을 사용하고, 종료 후 생성한 소식·사진·편집 잠금을 정리합니다.

## 문서 정보

- 기준 버전: `main`
- 최초 작성일: 2026-07-28
- 운영 주소: `https://bookstore-news-studio.rlawksml.chatgpt.site/`
- 자동 테스트 위치: `apps/web/tests/`
- 실행 명령: `npm run lint`, `npm test`, `npm run build`, `npm run test:integration:local`

## 우선순위와 실행 구분

| 구분 | 의미 |
|---|---|
| P0 | 입력 손실·권한 우회·사진 유실처럼 배포를 막아야 하는 핵심 시나리오 |
| P1 | 주요 사용자 흐름과 발행 결과에 직접 영향을 주는 시나리오 |
| P2 | 편의성·표시·보조 기능 시나리오 |
| 자동 | 코드 테스트 또는 실제 Supabase 통합 테스트로 반복 실행 |
| 수동 | 서로 다른 브라우저, 모바일 화면, 외부 게시판처럼 사람 확인이 필요한 항목 |
| 혼합 | 자동 보호 로직과 실제 화면 사용성을 함께 확인 |

## 공통 준비

- 환경 A: 소식 입력자용 데스크톱 브라우저
- 환경 B: 두 번째 입력자 또는 HTML 편집자용 별도 브라우저·시크릿 창
- 환경 C: 방문자용 모바일 기기 또는 로그인하지 않은 브라우저
- 테스트 전용 책방 1곳과 발행 월 1개
- 20MB 이하 JPEG·PNG 각 1장과 iPhone HEIC 1장
- 테스트 데이터 제목에는 `[테스트]`를 붙이고 종료 후 삭제
- 동일 브라우저의 여러 탭은 작업자 로그인 쿠키를 공유하므로 동시 작업 검증에는 사용하지 않음
- Production 점검은 공개 GET·읽기 전용 집계만 사용하고, 생성·수정·삭제 TC는 별도 Staging에서만 실행

## 0. 백업·복원 안전성

### TC-DR-001 · 백업 파일 무결성

- 우선순위/구분: P0 / 자동
- 사전조건: 저장소 밖에 생성한 백업 디렉터리
- 절차:
  1. `npm run backup:verify -- /절대/백업/경로`를 실행한다.
  2. DB JSON 한 파일 또는 복제한 사진 한 파일을 바꾼 테스트 fixture도 검증한다.
- 기대 결과:
  - 원본 백업은 모든 파일의 크기·SHA-256과 DB 행 수가 일치해 `PASS`다.
  - 변조된 fixture는 `FAIL`이며 복원 단계로 진행하지 않는다.

### TC-DR-002 · Production 복원 차단

- 우선순위/구분: P0 / 자동
- 절차:
  1. `APP_ENV=production`으로 복원 도구를 실행한다.
  2. 예상 Staging ref와 실제 URL ref를 다르게 설정한다.
  3. backup source fingerprint와 대상 fingerprint를 같게 설정한다.
- 기대 결과:
  - 세 경우 모두 Database·Storage 쓰기 전에 명령이 실패한다.
  - 실제 비밀값이나 URL은 테스트 로그에 출력되지 않는다.

### TC-DR-003 · 빈 Staging 실제 복원

- 우선순위/구분: P0 / 실제 Supabase Staging
- 사전조건: 운영과 분리된 빈 Staging, migration 적용, backup 검증 PASS
- 절차:
  1. 복원 dry-run에서 대상 ref, 빈 테이블·버킷, 예정 개수를 확인한다.
  2. `--execute`로 복원한다.
  3. 네 테이블과 원본·미리보기를 다시 읽고 manifest와 비교한다.
- 기대 결과:
  - 행 수·JSON fingerprint·사진 수·크기·SHA-256이 모두 일치한다.
  - Production에는 생성·수정·삭제 요청이 없다.
  - 하나라도 다르면 릴리스 판정은 `NO-GO`다.

## 1. 초기 로딩과 접속

### TC-LOAD-001 · 정상 초기 로딩

- 우선순위/구분: P0 / 자동·수동
- 사전조건: Supabase Database와 Storage 환경변수가 정상
- 절차:
  1. 로그인하지 않은 새 창에서 운영 주소를 연다.
  2. 초기 로딩 화면이 끝날 때까지 기다린다.
- 기대 결과:
  - 빈 흰 화면 대신 데이터 로딩 안내가 먼저 표시된다.
  - `/api/workspace` 성공 후 방문자 달력과 책방 소식이 표시된다.
  - 같은 요청이 불필요하게 반복되지 않는다.

### TC-LOAD-002 · 지연·실패 재시도

- 우선순위/구분: P1 / 자동
- 사전조건: 최초 데이터 요청을 지연 또는 실패하도록 테스트 대역 설정
- 절차:
  1. 첫 요청을 8초 이상 지연한다.
  2. 첫 번째와 두 번째 요청을 실패시키고 세 번째 요청을 성공시킨다.
  3. 세 요청을 모두 실패시키는 경우도 확인한다.
- 기대 결과:
  - 8초 후 지연 안내와 다시 시도 버튼이 표시된다.
  - 최대 3회까지만 자동 시도한다.
  - 최종 실패 시 빈 데이터로 오인하지 않고 연결 오류를 안내한다.

## 2. 작업자 접속과 세션

### TC-AUTH-001 · 입력자 암호와 자판 변환

- 우선순위/구분: P0 / 자동·수동
- 절차:
  1. `소식 입력`을 선택한다.
  2. 한글 자판과 영문 자판 상태에서 각각 입력자 암호를 입력한다.
- 기대 결과:
  - 두 자판 상태 모두 동일한 입력자 역할로 접속된다.
  - 실제 암호 값은 HTML·브라우저 번들·Git 저장소에 포함되지 않는다.

### TC-AUTH-002 · 역할별 API 권한

- 우선순위/구분: P0 / 자동
- 절차:
  1. 방문자 세션으로 책방·소식·사진 원본 변경 API를 호출한다.
  2. HTML 편집자 세션으로 입력자 전용 저장 API를 호출한다.
  3. 입력자 세션으로 허용된 저장 API를 호출한다.
- 기대 결과:
  - 방문자와 잘못된 역할은 401 또는 403으로 거부된다.
  - 올바른 역할과 탭 세션 ID가 함께 있을 때만 요청이 처리된다.

### TC-AUTH-003 · 새로고침·로그아웃·탭 종료

- 우선순위/구분: P1 / 혼합
- 절차:
  1. 입력자로 로그인하고 새로고침한다.
  2. 로그아웃 후 작업자 API를 호출한다.
  3. 탭을 닫고 새 탭에서 다시 접속한다.
- 기대 결과:
  - 같은 탭의 새로고침에는 역할이 유지된다.
  - 로그아웃 또는 탭 종료 후에는 암호 입력 없이 작업 화면에 들어가지 않는다.

### TC-AUTH-004 · 동일 브라우저 다중 탭

- 우선순위/구분: P2 / 수동
- 절차:
  1. 같은 브라우저의 탭 A에서 입력자로 로그인한다.
  2. 탭 B에서 다시 작업자로 로그인한다.
  3. 탭 A에서 저장 또는 편집 상태 갱신을 시도한다.
- 기대 결과:
  - 현재 구조에서는 공유 HttpOnly 쿠키가 탭 B 세션으로 교체돼 탭 A가 401을 받을 수 있다.
  - 실제 동시 사용자 검증은 별도 브라우저나 별도 기기에서 진행한다.
  - 향후 개선 시 탭 A에 세션 종료 안내를 표시하고 반복 요청을 중단한다.

## 3. 책방 기본정보

### TC-BOOK-001 · 책방 생성과 수정

- 우선순위/구분: P0 / 혼합
- 절차:
  1. 책방 관리에서 이름·지역·주소·전화·영업시간·SNS·홈페이지를 입력한다.
  2. 저장하고 책방 목록으로 돌아온다.
  3. 다시 책방 관리에 들어간다.
- 기대 결과:
  - 서버 성공 응답 후에만 저장 완료로 표시된다.
  - 입력한 값이 목록과 재진입 화면에 동일하게 남는다.
  - 지역과 주소는 각각의 필드로 보존된다.

### TC-BOOK-002 · 책방 저장 실패 보존

- 우선순위/구분: P0 / 자동
- 절차:
  1. 책방 저장 API에 일시적인 5xx를 반환한다.
  2. 재시도가 모두 실패하도록 한다.
- 기대 결과:
  - 입력 폼을 초기화하지 않는다.
  - 저장 실패를 안내하고 사용자가 다시 저장할 수 있다.

## 4. 소식 입력·자동 저장·완료

### TC-SUB-001 · 마지막 글자까지 뒤로가기 저장

- 우선순위/구분: P0 / 자동·수동
- 절차:
  1. 제목과 상세 내용을 입력한다.
  2. 마지막 글자를 입력한 직후 `← 책방 목록`을 누른다.
  3. `임시 저장 후 이동`을 선택한다.
  4. 같은 책방에 다시 들어간다.
- 기대 결과:
  - 목록 이동 전에 화면의 정확한 마지막 스냅샷을 서버가 확인한다.
  - 제목과 상세 내용의 마지막 글자까지 복원된다.

### TC-SUB-002 · 새로고침 임시 복구본

- 우선순위/구분: P0 / 자동
- 절차:
  1. 서버 자동 저장이 끝나기 전에 내용을 입력한다.
  2. 같은 탭에서 새로고침한다.
  3. 서버에 더 최신 버전이 있는 경우도 확인한다.
- 기대 결과:
  - 같은 서버 버전이면 탭의 임시 복구본으로 마지막 입력을 복원한다.
  - 서버가 더 최신이면 오래된 복구본을 폐기하고 서버 내용을 사용한다.

### TC-SUB-003 · 필수 항목 검증

- 우선순위/구분: P1 / 자동·수동
- 절차:
  1. 소식 제목 또는 상세 내용을 비운다.
  2. `입력 마무리`를 누른다.
- 기대 결과:
  - 완료 상태로 바뀌지 않는다.
  - 첫 번째 누락 필드로 스크롤·포커스가 이동한다.

### TC-SUB-004 · 입력 완료 서버 확인

- 우선순위/구분: P0 / 자동·수동
- 절차:
  1. 필수 내용을 모두 작성한다.
  2. `입력 마무리`를 누른다.
  3. 완료 저장 API를 성공시키는 경우와 실패시키는 경우를 각각 확인한다.
- 기대 결과:
  - 서버 저장 성공 후에만 목록으로 이동하고 `입력 완료`가 표시된다.
  - 실패하면 편집 화면에 남고 상태를 `작성 중`으로 유지한다.

### TC-SUB-005 · 완료 후 수정

- 우선순위/구분: P1 / 자동·수동
- 절차:
  1. 입력 완료된 소식을 다시 연다.
  2. 제목 또는 상세 내용을 수정한다.
- 기대 결과:
  - 상태가 자동으로 `작성 중`으로 전환된다.
  - 이미 게시된 소식이면 재게시 필요 상태가 표시된다.

### TC-SUB-006 · 지난달 내용 복사

- 우선순위/구분: P1 / 수동
- 절차:
  1. 이전 달에 소식이 있는 책방을 선택한다.
  2. 새 발행 월에서 `지난달 소식 불러오기`를 누른다.
- 기대 결과:
  - 이전 달 원본은 변경되지 않는다.
  - 새 달의 독립적인 작성 중 소식으로 복사된다.

### TC-SUB-007 · 저장하지 않고 이동

- 우선순위/구분: P0 / 자동·수동
- 절차:
  1. 이미 한 번 자동 저장된 소식의 제목과 상세 내용을 다시 수정한다.
  2. 자동 저장이 실행되기 전에 `← 책방 목록`, 로고 또는 로그아웃을 누른다.
  3. 이탈 안내에서 `계속 작성`을 눌러 화면에 남는지 확인한다.
  4. 다시 이탈 안내를 열고 `저장하지 않고 이동`을 선택한다.
  5. 같은 책방에 다시 들어간다.
- 기대 결과:
  - 안내에는 `임시 저장 후 이동`, `계속 작성`, `저장하지 않고 이동`이 모두 표시된다.
  - `계속 작성`은 현재 입력을 그대로 유지한다.
  - `저장하지 않고 이동`은 예약된 자동 저장과 탭 임시 복구본을 취소한다.
  - 마지막으로 서버가 확인한 자동 저장 내용까지만 복원되고 그 이후 수정은 사라진다.
  - 한 번도 서버에 저장되지 않은 새 소식은 빈 임시 레코드로 남지 않는다.
  - 사진 업로드 중에는 세 선택지 모두 이동을 실행하지 않는다.

## 5. 소식·사진 순서 변경

### TC-SORT-001 · 입력 텍스트 선택

- 우선순위/구분: P0 / 자동·수동
- 절차:
  1. 제목 input과 상세 textarea 안의 문장을 마우스로 드래그한다.
  2. 소식 카드의 빈 영역도 드래그한다.
- 기대 결과:
  - 텍스트만 선택되고 소식 순서는 바뀌지 않는다.
  - 카드 전체에는 `draggable` 속성이 없다.

### TC-SORT-002 · 전용 손잡이 정렬

- 우선순위/구분: P1 / 자동·수동
- 절차:
  1. 소식을 두 개 이상 만든다.
  2. `⠿ 소식 n 순서 이동` 버튼을 끌어 순서를 변경한다.
  3. 사진 번호 손잡이와 화살표 버튼으로 사진 순서를 변경한다.
- 기대 결과:
  - 전용 버튼에서만 드래그가 시작된다.
  - 저장 후 재진입해도 변경된 순서가 유지된다.

## 6. 사진 업로드와 복구

### TC-IMG-001 · JPEG·PNG 여러 장 업로드

- 우선순위/구분: P0 / 실제 Supabase 통합·수동
- 절차:
  1. JPEG와 PNG를 동시에 선택한다.
  2. 업로드 완료 후 목록으로 나갔다가 다시 들어간다.
- 기대 결과:
  - 원본은 비공개 버킷, JPEG 미리보기는 공개 버킷에 저장된다.
  - 목록 사진 수와 재진입 사진 수가 일치한다.

### TC-IMG-002 · HEIC·HEIF 업로드

- 우선순위/구분: P0 / 자동·수동
- 절차:
  1. MIME이 정상인 HEIC와 MIME이 비어 있는 HEIC를 각각 선택한다.
  2. 미리보기 생성과 원본 저장을 기다린다.
- 기대 결과:
  - 확장자로도 HEIC·HEIF를 판별한다.
  - 원본은 HEIC로 보관하고 방문자용 JPEG 미리보기를 만든다.
  - 변환 중에는 명확한 진행 안내가 표시된다.

### TC-IMG-003 · 드래그 앤 드롭

- 우선순위/구분: P1 / 수동
- 절차:
  1. 여러 사진을 업로드 영역에 끌어다 놓는다.
  2. 같은 파일에 `drop`과 `change`가 연달아 발생하는 환경을 확인한다.
- 기대 결과:
  - 한 번의 사용자 동작으로 중복 사진이 생기지 않는다.
  - 드롭 이벤트가 소식 카드 정렬 이벤트로 전파되지 않는다.

### TC-IMG-004 · 업로드 중 이동 차단

- 우선순위/구분: P0 / 자동·수동
- 절차:
  1. HEIC 또는 큰 JPEG 업로드를 시작한다.
  2. 완료 전에 뒤로가기·임시 저장·입력 마무리를 시도한다.
- 기대 결과:
  - 업로드 대상 입력과 저장·완료 버튼이 잠긴다.
  - 사진의 Storage 저장과 DB 연결이 끝난 뒤에만 이동할 수 있다.

### TC-IMG-005 · 서명 URL·네트워크 복구

- 우선순위/구분: P0 / 자동
- 절차:
  1. 첫 번째 Storage PUT에 네트워크 오류 또는 재시도 가능한 상태를 반환한다.
  2. 같은 서명 주소 재시도를 모두 실패시킨다.
- 기대 결과:
  - 같은 주소에서는 제한된 횟수만 재시도한다.
  - 이후 새로운 서명 URL을 발급받아 다시 전송한다.
  - 최종 실패한 임시 경로는 DB에 연결하지 않는다.

### TC-IMG-006 · 잘못된 파일과 용량 제한

- 우선순위/구분: P0 / 자동
- 절차:

### TC-IMG-007 · 사진 삭제 실패 복구

## 7. 동시 편집과 충돌

### TC-CONC-001 · 같은 책방 진입 잠금

- 우선순위/구분: P0 / 실제 Supabase 통합·수동
- 절차:
  1. 환경 A에서 책방과 월을 열어둔다.
  2. 환경 B에서 같은 책방과 월에 들어간다.
- 기대 결과:
  - 환경 B는 안내 팝업만 보고 편집 화면에 들어가지 않는다.
  - 다른 책방은 정상적으로 열 수 있다.

### TC-CONC-002 · 편집 임대 해제와 만료

- 우선순위/구분: P0 / 실제 Supabase 통합·수동
- 절차:
  1. 환경 A에서 목록으로 정상 이동한다.
  2. 환경 A를 강제 종료하는 경우도 확인한다.
- 기대 결과:
  - 정상 이동 시 임대가 즉시 해제된다.
  - 강제 종료 시 최대 3분 후 다른 작업자가 인계할 수 있다.
  - 다른 세션은 소유하지 않은 임대를 삭제할 수 없다.

### TC-CONC-003 · 낙관적 저장 충돌

- 우선순위/구분: P0 / 자동·실제 Supabase 통합
- 절차:
  1. 두 세션이 같은 `updated_at`을 가진 소식을 읽는다.
  2. 세션 A가 먼저 저장한다.
  3. 세션 B가 다른 내용으로 저장한다.
  4. 응답만 유실된 동일 내용 재시도도 확인한다.
- 기대 결과:
  - 다른 내용은 409로 막고 최신 내용 확인을 안내한다.
  - 서버에 이미 저장된 동일 내용이면 최신 버전을 이어받아 성공으로 복구한다.

- 이번 실행에서는 운영 데이터를 수정하는 브라우저 수동 TC를 반복하지 않았다. 직전 2026-07-27 운영 검증에서 실제 JPEG·HEIC 업로드, 뒤로가기 저장, 재진입 사진 2장 복원과 테스트 데이터 정리를 완료했다.

### 관찰된 비차단 경고

1. 빌드가 HEIC 변환기 지연 로드 청크의 500KB 초과를 경고했다. 일반 방문자와 JPEG 입력 시 내려받지 않고 HEIC를 선택할 때만 로드되므로 이번 배포 차단 사유는 아니다. 모바일 성능 TC에서 실제 다운로드 시간과 메모리를 별도로 측정한다.
2. 최근 운영 Worker 오류 로그에는 `/favicon.ico` HTTP 404 한 건만 있었다. 화면·저장·사진 API 오류는 아니며 사이트 아이콘을 추가하면 제거할 수 있다.
